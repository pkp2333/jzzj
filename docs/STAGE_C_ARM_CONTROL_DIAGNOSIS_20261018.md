# C 阶段左臂闭环调用诊断与解决方案

检查日期：2026-10-18；代码基线：`8089c57`，分支 `refactor/stage-c-layout`。
后续本地修复与验证见 [修复记录](STAGE_C_ARM_CONTROL_REPAIR_20261018.md)。以下保留检查当时的现象。
本轮只读检查实际硬件，并在独立 ROS master `11339` 上运行运动学与模拟 SDK 测试；未向实体机械臂发送目标或扭矩指令，未修改控制实现或现场标定。

## 结论

已复现两个可阻断闭环的问题：外部旧抓取脚本的路径、参数文件和节点私有命名空间不匹配；逆解在关节限位边界附近产生小幅数值超限，导致可保持的当前末端位姿也被拒绝。

当前 I2C 状态已经恢复，不能继续用此前“控制板地址无应答”的状态解释本轮故障。此次未验证实体舵机写入、扭矩或负载运动。

## 证据

### 1. 当前回读正常，生产 ROS 尚未运行

- 重连后 `i2cdetect -y -r 1 0x10 0x11` 能看到 `10 11`。
- 两轮各三次 SDK 回读均为 `[89, 3, 90, 90, -1, 60]` 度。这里只证明 SDK 返回了有效范围内的数据，不证明串口缓存新鲜度或实际动作。
- 按现场 `servo_signs=[1,-1,1,1,1,1]` 换算的模型角度为 `[89,-3,90,90,-1,60]` 度。
- 检查时生产 ROS master 不可连接，且没有机械臂轨迹驱动、C server 或运动学节点。此前只观察入口也不会发送轨迹。

### 2. 外部旧启动脚本存在确定性错误

现场 `/home/orangepi/start_stagec_grab.sh` 仍然：

1. 从已清理的 `/home/orangepi/jzzj-stagec/deploy` 读部署配置，从外部旧 mission 工作空间读运动学模板。
2. 把旧版 `user_params/params/arm_config.yaml` 当作新轨迹驱动参数；该文件缺少 `hardware_enabled`、`servo_signs` 等驱动必需字段。
3. 将参数加载到 `/arm_left/arm_trajectory`，却使用 `rosrun ... arm_trajectory_node.py __ns:=arm_left`。脚本内 `rospy.init_node('arm_trajectory_node')` 使节点私有命名空间成为 `/arm_left/arm_trajectory_node`，读不到前者的参数。
4. 没有失败即退出检查，配置加载或后台节点失败后仍可能打印启动完成；也没有生成当前会话的停车交权心跳。

轨迹驱动在 `catkin_ws/src/actuator/arm/scripts/arm_trajectory_node.py:18` 检查必需开关，参数不匹配会在访问舵机前退出。历史日志也存在 `/arm_left/arm_trajectory_node` 启动后立即退出的记录；另一次 15:04 的日志明确出现 `arm feedback rejected: invalid SDK feedback`，属于此前的反馈故障，不能当作当前回读结果。

### 3. 当前位姿原样逆解仍被拒绝

使用现场配置、上述测得的关节角及已构建的 `stage_c_kinematics`，在隔离 ROS 中执行：

- FK 成功，TCP 坐标为 `(-0.0805070632, -0.1373395930, 0.0318811867) m`。
- 把完整 FK 位姿原样作为 IK 目标，返回 `valid=false`，原因为 `IK limits/continuity violation`。
- 对位姿做毫米级偏移的试验也被拒绝；偏移目标是否可达需要独立验证，不能仅由拒绝结果判错。

直接调用同一厂商运动学库，当前位姿的逆解结果为：

| 关节 | 当前角度 / ° | 厂商逆解 / ° | URDF 上限 / ° |
|---|---:|---:|---:|
| 1 | 89 | 88.99999842 | 135.00031569 |
| 2 | -3 | -3.01921234 | 90.00021046 |
| 3 | 90 | **90.01931810** | **90.00021046** |
| 4 | 90 | 89.97922417 | 90.00021046 |
| 5 | -1 | -1.00011011 | 135.00031569 |

第 3 关节超出上限约 `0.0191°`。`mission_ws/src/mission/jzzj_grasp/src/kinematics_node.cpp:54` 严格拒绝该候选，而当前反馈 `seed` 没有传入厂商求解接口，只用于求解后的连续性比较。

`backends.py:124` 随即把无效解转成失败结果，所以该路径不会执行后续 `send_goal` 和舵机目标写入。

对照实验：以当前反馈为初值的 KDL LMA 对相同位姿返回成功，位置残差为零。该实验验证了同位姿回归的可行性，不等于已实现完整限位求解或验证全部工作区。

### 4. Action 到 SDK 的软件接线可以工作

独立 ROS master 中运行正式 `arm_trajectory_node.py`，只将 `Arm_Lib` 替换为内存模拟，不打开 I2C。使用正确的 `/arm_left/arm_trajectory` 私有参数：

- 向 `/arm_left/follow_joint_trajectory` 发送第 5 关节增加 `5°` 的目标。
- 捕获到 SDK 调用 `[89,3,90,90,4,60,800]`，前六项为 SDK 角度，最后一项为毫秒。
- Action 返回 `SUCCEEDED`、`error_code=0`，耗时约 `3.095 秒`。

因此该模拟范围内的关节顺序、弧度/角度换算与轨迹回调有效；实体执行和底层固件写入仍待验证。

### 5. 回读速度与错误传播还需整改

- 实测三次六关节回读耗时：`0.642085`、`0.642109`、`0.642068 秒`。SDK 每个关节读取后固定等待 `0.1 秒`，六关节采样理论上限约 `1.56 Hz`。驱动的 `0.1 秒`定时器不能使它达到 10 Hz。
- 驱动要求连续三次新反馈稳定，必须把回读周期、运动时间和排队延迟计入到位与停止超时。当前数据尚不足以断言已发生到位超时。
- 使用只会抛出 I/O 异常的模拟总线，SDK 的 `Arm_serial_servo_write6` 打印错误后仍正常返回 `2366`。该数值是最后一个位置编码，不是执行成功标志。轨迹驱动虽会继续等待反馈，但无法立即收到写失败异常。

## 整改顺序

### P1：统一闭环启动与会话

停用上述外部旧入口，使用工程内 `tools/stage_c/start_control.sh real`。它通过 launch 将 `deploy/arm.yaml` 加载到实际轨迹节点的私有命名空间，并启动运动学和 C server。

启动后应同时具备：`/stage_c/grasp`、`/stage_c/compute_arm_motion`、`/arm_left/follow_joint_trajectory` 和新鲜的 `/arm_left/joint_states`。真实任务还需要同一 session 的底盘锁定及控制权心跳；现场单次工具的调试心跳由操作员确认交权，不能当作底盘的实测停车证据。

### P1：修复逆解边界处理

1. 使用实测关节角作为初值，优先求取邻近分支，并在求解过程中处理关节上下限。
2. 保持现有关节限制和 `max_joint_step_rad`。对明确规定的微小数值误差，可将候选投影回合法边界，但必须再次通过位置/姿态 FK 残差及连续性校验；真正超限或不可达的目标继续拒绝。
3. 将统一错误拆成关节号、候选值、上下限、相对 seed 差值，区分数值边界、真实超限、分支跳变及不可达。
4. 首先让“当前位姿原样逆解”回归通过，再验证工作区内部位姿、毫米级可达位移、边界及不可达位姿。限位与残差验收标准不得以“舵机动了”代替。

### P2：改善反馈与 SDK 错误传播

先核验固件批量反馈协议，再实现项目内的批量读取适配，减少六次固定等待，并记录采样起止时间。根据测得的最差周期调整到位和停止时限。项目适配层应明确抛出 I/O 失败；保持失败锁存，不把 SDK 返回值当作运动成功。

## 实机验证顺序

1. 回读与启动检查通过，确认只存在一个左臂控制者。
2. 在空载条件下先验证当前姿态保持，再做一个关节的受限小角度动作，检查实际角度变化、方向和取消保持。
3. 验证“当前 TCP 不变”和工作区内的小步 Cartesian 目标，再恢复完整 C 阶段流程。

真实启动和 Action 会使能机械臂；本轮未执行上述动作，也未重新校准坐标、关节符号或 TCP。
